1. Read the meeting minutes.
2. Produce the markdown output, as before.
3. Add the tasks to the tuxedo CLI app.

| Question | Answer |
|---|---|

## Investigation

### The tuxedo CLI

`tuxedo --help` names the commands. The real behavior needed a test, so I ran
one in the scratchpad with `TODO_DIR` pointed at a throw-away file. Four facts
came out of it. All four are now written into the workflow:

1. A task text that holds `due:YYYY-MM-DD` is stored word for word. The words
   "Monday" and "on Friday" survive inside it.
2. A task text with no `due:` field loses its date words. The parser pulls them
   out and makes `due:` and `rec:` from them. "Prepare the Monday standup deck"
   became "Prepare the standup deck due:2026-09-21".
3. `tuxedo replace N TEXT` stores the text word for word and parses no date. It
   drops the creation date. A repair must put the date back.
4. `tuxedo add` puts the creation date in front of the text by itself.

`tuxedo lsprj` and `tuxedo lsc` gave the projects and the contexts already in
use, such as `+knowledge_graph`, `+iso27000`, `@Gayan`. The Tasks phase reuses
them instead of inventing new names.

### The vault

The command file names the folders. The real note format came from the vault:

- `~/Notes/_meta_/_templates_/MeetingMinutes.md` holds the house structure, and
  the two `tasks` query blocks for "Me" and "Team".
- `~/Notes/02_Calendar/Meeting_Notes/2026-09-17 Rollback and Feature based
  Deployment (Risk).md` shows a finished note: `[[Full NAME|First]]` attendee
  links, `#me`, and the action line
  `- [ ] added:[[date]] i:H u:H #me <text> due:[[date]]`.
- `~/Notes/02_Calendar/Meeting_Notes/2026-09-17 ISO 27000 Q&A Discussion.md`
  shows a stub note, the second input form the workflow accepts.
- `~/Notes/02_Calendar/Daily_Notes/2026-09-17.md` shows the `## Schedule`
  section. The workflow reads it when the caller gives no input, and it adds the
  link to the new note there.

### The workflow pattern

`.claude/workflows/debug-ticket.js` gave the shape: `meta` with named phases,
one JSON schema per phase, a prompt function per agent, a shared rules block,
and a status field in every early return. `.claude/workflows/README.md` gave the
documentation pattern.

## Changes

### `.claude/workflows/summarize-meeting.js` (new, 460 lines)

Three phases, one agent each.

1. **Read**. Runs `date +%F`. Resolves the input: a path under `Meeting_Notes`
   is a stub to merge into, any other file is a transcript, text is a
   transcript, nothing makes it read today's schedule and return the status
   `needs_input` with the meetings it found. A path that points at no file is an
   error, never transcript text. Returns the meeting facts against a schema:
   title, date, attendees, chair, agenda, discussion, decisions, action items,
   parking lot, next meeting.
2. **Minutes**. Writes the note. Merges into the existing note and keeps every
   human line. Adds the link to the daily note when it is missing.
3. **Tasks**. Turns each action item into one `tuxedo add`. The priority comes
   from the importance and urgency pair. The owner becomes the context. The
   project comes from `tuxedo lsprj`. Every task carries an explicit `due:`
   date. The phase reads the list back and repairs a damaged line.

### `.claude/commands/summarize-meeting.md` (rewritten, 219 lines to 55)

The prompt content moved into the workflow. The command is now a launcher. It
calls the workflow, and it handles the four statuses.

### `.config/opencode/commands/summarize-meeting.md` (changed)

opencode has no Workflow tool, so this copy stays self-contained. It gained
"Step 8: Add the action items to tuxedo", with the same mapping tables and the
same four measured tuxedo rules.

### `.claude/workflows/README.md` (changed)

Added the `## summarize-meeting` section: the three input forms, the arguments,
the three places the workflow writes, and the priority mapping table.
