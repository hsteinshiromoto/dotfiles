# 2026-09-29

## A Neovim Bridge to the Notes Vault's Template Renderer

### Initial request

"Update all template notes to work with neovim and obsidian similarly to how the
daily notes work."

### Problem

The work vault at `~/Notes` writes every template in Templater syntax (`<% %>`).
obsidian.nvim reads `{{key}}` only. Its `:Obsidian template` therefore inserted the
tags verbatim, and seven templates that prompt for a title were unusable outside
Obsidian.

The two dialects cannot share a file. Whichever engine runs leaves the other's tags
as literal text. The user chose to have Neovim call the vault's own renderer,
`bin/render_template.py`, which the vault already uses for `make` and its
daily-notes pipeline.

### Accepted solution

New file `lua/utils/obsidian_template.lua`, one job per function:

1. `vault_root` — `vim.fs.root(0, ".obsidian")`, so the bridge works in any vault, not
   only the ones listed in the `workspaces` option.
2. `interpreter` — prefers the vault's `.venv/bin/python`, falls back to `python3`.
   The renderer imports only the standard library, so the fallback is real.
3. `templates`, `describe`, `render` — thin wrappers over `vim.system`. A template that
   prompts takes two calls, because the renderer cannot show a dialog: `--describe`
   lists the prompts, Neovim asks, `--json` renders with `--var` answers and returns
   the filename the template renames to.
4. `folder` — reads Templater's own `data.json` for the folder a template maps to, so
   Neovim and Obsidian file a note in the same place and cannot drift apart.
5. `apply` — renders into the current buffer and renames the file in place. This is
   what Templater does in Obsidian.
6. `create` — makes a new note from a template.

`lua/plugins/obsidian.lua`: `<localleader>ot` and `<localleader>on` now call
`:ObsidianTemplate` and `:ObsidianNoteFromTemplate`. `config` calls the bridge's
`setup()`.

### A bug the tests caught

`create` first asked for a title and then asked the template's own prompts. For
`Person.md` and `Project.md` the prompt variable is `Title`, and the template guards it
with `if (Title.startsWith("Untitled"))`. Supplying a real title makes that guard
false, so the prompt answer was collected and then silently thrown away. The user was
asked twice and one answer was ignored.

`create` now keeps the title as `Untitled` when a template declares prompts, and asks
for a title only when it declares none. A template that prompts names the note itself.

### Sanity check

Fifteen headless checks against a sandbox vault that symlinks the real renderer and
templates. All pass: vault detection, interpreter choice, template listing, the
Templater folder map, `describe`, `render`, `apply` (buffer replaced, file renamed,
old file removed, no raw tags left), and both `create` paths.

The sandbox keeps the test out of the real vault. `nvim --headless` needs `-n`, or a
leftover swap file blocks the run with a prompt nobody can answer.

### Cross-file relationships

- `~/Notes/bin/render_template.py` was extended in the same session to run `<%* %>`
  execution blocks and to accept `--describe`, `--var` and `--json`. The bridge is the
  caller of that contract. See `~/Notes/journal/2026-09-29.md`.
- `~/Notes/.obsidian/plugins/templater-obsidian/data.json` holds the template-to-folder
  map. The bridge reads it rather than repeating it.
- `lua/plugins/obsidian.lua` still carries a large `templates.substitutions` table of
  `{{KEY}}` functions. No template in the vault contains `{{`, so it is dead code under
  this design. Left in place. Deleting it is a separate change.
- The `workspaces` list in the same file names `~/Work/LOR/Notes` and
  `~/Projects/recipes/content/`. Neither exists on this host. The real vault is
  `~/Notes`. The bridge does not read that list, so it works anyway. Left alone.
