# 2026-10-19

## A duplicated `$fpath` made zsh rebuild its completion cache on every shell

### The request

Ghostty felt slow. The report covered two symptoms: a new window or pane took
seconds to show a prompt, and typing felt laggy once the prompt arrived.

### The terminal was not at fault

An interactive zsh took 5.94 s, 8.46 s and 8.12 s over three runs. A timestamped
`zsh -i -x` trace put 8.9 s of 9.9 s inside `compinit`, `compdump` and `compdef`.
Ghostty starts `zsh -c "tmux attach || tmux new"`, so every pane paid this cost.

`compinit` discarded `~/.zcompdump` and rebuilt it every time. The trace shows the
cache check and its result:

```
compinit:489> [[ _i_autodump -eq 1 && 1525 -eq 1327 ]]
```

The two numbers come from two different counts of the same files. `compdump:26`
counts over the raw `$fpath`. `compaudit:62` counts over a de-duplicated copy,
because `compaudit:45` declares `local -a -U +h fpath`. `compinit` compares the
value `compdump` wrote against the value `compaudit` computed. While `$fpath`
holds duplicates the two can never agree, so the cache was always invalid.

### The duplicates come from an exported `FPATH` and a nested shell

`$fpath` held 44 entries for 19 unique directories. nix-darwin writes
`/etc/zshenv`, which prepends three directories for each entry in `$NIX_PROFILES`.
That file guards itself with a plain shell variable, not an exported one, so the
guard does not survive into a child shell. zsh exports the array as `FPATH`
(`export -T FPATH fpath`). Each nested shell therefore inherits an
already-prepended `$fpath` and prepends again. Ghostty starts a shell, that shell
starts tmux, and tmux starts a login shell, which is three rounds.

### The fix is one line, and it must sit in `.zshenv`

A new `~/.zshenv` sets `typeset -U path fpath`. `.zshrc` is too late: zsh reads
`/etc/zshrc` first, and nix-darwin runs its own `compinit` there. `~/.zshenv` runs
after `/etc/zshenv` prepends and before `/etc/zshrc` counts.

`$fpath` dropped to 19 entries. The `.zcompdump` modification time stopped
changing, which confirms the cache now holds. Startup went to 0.51 s, 0.56 s and
0.63 s. The CPU figures are the cleaner measure, because they do not move with
disk contention: user time fell from 0.50 s to 0.09 s and system time from 0.67 s
to 0.08 s. Completion still works, with 2020 entries in `$_comps`.

Five stale `.zcompdump.HumbertoMBP2025.local.<pid>` files were removed. They dated
from May to October and nothing reads them.

### The first explanation of the typing lag was wrong

The first answer blamed `ZSH_AUTOSUGGEST_STRATEGY`, which `atuin init zsh` sets to
`atuin history`. The claim was that the atuin query ran on the keystroke path. It
does not. zsh-autosuggestions sets `ZSH_AUTOSUGGEST_USE_ASYNC` itself on zsh 5.0.8
and later, at `zsh-autosuggestions.zsh:862`. Async was already on.

The cost is real but arrives another way. Read
`_zsh_autosuggest_async_request`. On every keystroke it sends `kill -TERM` to the
previous child, forks this fully loaded shell through a process substitution, and
then blocks on `read` for the child process ID. The 20.97 ms atuin query runs off
the main thread. The fork and the blocking read do not.

`ZSH_AUTOSUGGEST_STRATEGY=(history)` now follows the `atuin init` line. The
built-in strategy measures 2.83 ms against 20.97 ms. Atuin keeps Ctrl-R, which is
what it is for, and only the inline grey suggestion changes source.

Three settings now precede the zgenom `source` line, because the plugin reads them
when it loads. `ZSH_AUTOSUGGEST_MANUAL_REBIND=1` turned out to be the larger win of
the three. Without it the plugin re-binds its widgets on every prompt. With it,
`_zsh_autosuggest_start` runs `add-zsh-hook -d precmd _zsh_autosuggest_start` and
removes itself, which takes 8.49 ms off each prompt. `ZSH_AUTOSUGGEST_USE_ASYNC=1`
pins behavior that a version test would otherwise decide.
`ZSH_AUTOSUGGEST_BUFFER_MAX_SIZE=60` stops the fetch on long lines.

The steady-state prompt chain fell from about 15 ms to about 6.3 ms.

### Loose ends

`eval "$(zoxide init zsh)"` moved after the atuin line. zoxide prints a startup
warning when anything initializes after it, and that warning reached stderr on
every shell.

`__zgenom_autoupdate_background` still costs 4.55 ms on every prompt to test a
seven-day timer. A manual `zgenom update` would remove it. This was left alone.

The rendering half of the report is not answered. Keystroke latency inside a real
terminal cannot be measured from a subprocess with no controlling TTY. An A/B
across tmux, plain Ghostty and `zsh -f` will separate tmux from the Metal renderer
on the 3440x1440 display. `window-vsync = false` is the next thing to test if the
renderer is at fault.
