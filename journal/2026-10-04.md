# 2026-10-04

## Request

Recommend better triggers for `.config/espanso/match/obsidian.yml`.

## What was wrong with the old triggers

The file held ten matches shaped `[[today]]`, `[[yesterday]]`, `[[tomorrow]]` and
`[[next monday]]` through `[[next sunday]]`. Four separate defects, three of them
confirmed by running something rather than by reading.

| Defect | Evidence |
|---|---|
| Bracketed triggers fight Obsidian | Typing `[[` auto-inserts `]]` and opens the link suggester, so espanso injects into an open popup |
| `date -v` is BSD only | `date -d "+1 days"` on this host returns `illegal option -- d`; the repo is named `dotfiles.linux` and stows to both |
| Ninety lines of near-duplicate YAML | The seven weekday matches differed by three characters each |
| `next monday` could return today | BSD `date -v+mon` stays on today when today is a Monday, so the link pointed at the note you were already in |

Only daily notes had triggers, although both vaults keep weekly, monthly,
quarterly and yearly notes.

## Two findings that changed the design mid-build

The first design kept `word: true`, copied from the old file, and considered a
regex for the weekdays. Both were wrong.

**`word: true` delays the expansion.** Espanso's rolling matcher fires a
`right_word` trigger only once a separator arrives *after* it. The test in
`espanso-match/src/rolling/matcher.rs` is explicit: `"hi"` alone yields no match,
`"hi,"` yields one. A bracketed trigger ends in `]`, which is itself a separator,
so the old file never paid this cost. `;td` would have sat there until the space
bar. `match/git.yml` already omits `word: true` on its nine `;` triggers, so
dropping it is also the house style.

**No trigger may be a prefix of another.** Espanso expands the shorter one as soon
as it matches, and it does not wait for more input
([espanso#178](https://github.com/espanso/espanso/issues/178)). This is a hard
constraint on the table, not a preference. It kills `;month` outright, because
`;mon` comes first. It was checked mechanically across all three match files, not
by eye: 59 triggers, zero collisions.

A regex trigger was rejected for a different reason. It cannot carry a per-weekday
alias, and the user asked for the relative word (`next monday`) after the pipe.

## What was built

`.config/espanso/scripts/obsidian_date.py`, a resolver that turns one spec into one
note name on stdout. Standard library only and Python 3.9 compatible, because the
espanso LaunchAgent runs with `PATH=/usr/bin:/bin:/usr/sbin:/sbin` and
`/usr/bin/python3` there is 3.9.6. Six small pure functions plus a `main`. Two
deliberate details:

- `next_weekday` and `last_weekday` use `timedelta(days=delta or 7)`. The `or 7` is
  the whole fix for the Monday bug.
- `iso_week` reads `isocalendar()[0]`, not `strftime("%Y")`. 2025-12-29 belongs to
  `2026-W01`, and `%Y` would call it `2025-W01`. This matches the Thursday rule in
  `~/.config/nvim/lua/plugins/obsidian.lua:61`, so espanso and Neovim agree without
  sharing code.
- `shift_months` anchors on the 15th and works in `(year, month)` integer space, so
  a `+1` from 31 January cannot overflow into March.

`obsidian.yml` became 23 matches, 45 triggers, every one calling the resolver
through `%CONFIG%`. The arguments are passed as an argv list, not a shell string,
so nothing is interpolated into a shell.

| Trigger | Alias | Result on Sunday 2026-10-04 |
|---|---|---|
| `;td` | `;today` | `[[2026-10-04\|today]]` |
| `;yd` | `;yesterday` | `[[2026-10-03\|yesterday]]` |
| `;tm` | `;tomorrow` | `[[2026-10-05\|tomorrow]]` |
| `;mon`…`;sun` | `;nextmon`…`;nextsun` | `[[2026-10-05\|next monday]]` |
| `;lmon`…`;lsun` | `;lastmon`…`;lastsun` | `[[2026-10-02\|last friday]]` for `;lfri` |
| `;wk` `;nwk` `;lwk` | `;week` `;nextweek` `;lastweek` | `[[2026-W40\|this week]]` |
| `;mth` | none, `;mon` blocks it | `[[2026-10\|this month]]` |
| `;qtr` | `;quarter` | `[[2026-Q4\|this quarter]]` |
| `;yr` | `;year` | `[[2026\|this year]]` |

`;sun` returning 2026-10-11 rather than 2026-10-04 is the Monday bug, verified on
the day that triggers it.

Tests are doctests inside the docstrings, 33 of them, run by a new `make
espanso-test`. The repository has no `pyproject.toml`, no `uv.lock` and no tests
directory, so pytest would have meant new scaffolding for one 200-line script.

## Verification

Doctests pass. `obsidian.yml` parses under `yq` with 23 matches. All 45 triggers
appear in `espanso match list` after `espanso restart`. The resolver was run under
`env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin`, which is the real runtime, not the
interactive shell. `espanso log` shows zero errors from `obsidian.yml`.

Still needs a human at a keyboard: typing the triggers in Obsidian and in Neovim.
Espanso watches keystrokes, so no script can stand in for that.

## Found, not fixed

`match/dates.yml` is broken in six ways, and espanso says so at every start:

```
unable to compile regex: '(?p<offset>[+-]\d+)(?p<unit>[dwmy])', error: unrecognized flag
```

Lowercase `p` is not valid Rust regex syntax, so two of the five matches never
compile. Five more defects sit behind that one.

1. `replace: "[[output]]"` is missing its braces, so it emits the literal word.
2. `date -d` is GNU and fails on this host.
3. `%y` gives a two-digit year, which matches no note name.
4. All five matches share one regex, so at most one can ever win.
5. The Python variant needs a 3.10 `match` statement and `dateutil`, on a 3.9
   stdlib-only interpreter.

The README claim that `dates.yml` offers a choice of five
output formats is therefore not true. Left alone as out of scope.
